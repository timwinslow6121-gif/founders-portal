## 👤 CUSTOMER PROFILE — structured fields + editability (Tim, 2026-08-27)
_Four gaps Tim hit using the profile. **Verified against prod first — and the headline finding is that all four fields are effectively UNUSED**, which changes what "fix" means._

| field | populated (of 5,461) |
|---|---|
| `medicaid_level` | **1** — and its value is `"No"`, not one of the intended levels |
| `language` | **0** |
| `lead_source` | **2** |
| `pharmacy_id` | **6** |

- 📌 **The dropdown is necessary but NOT sufficient.** These aren't fields agents avoid because they're free text — nobody fills them at all. A picker won't change that on its own; what makes a tag worth entering is a **filter that produces a worklist** (exactly the argument behind the coverage-tagging spec). Pair any picker work with the reason to use it. **Upside: with ~zero existing values there is no migration risk** — a controlled vocabulary can be imposed cleanly right now, with no free-text mess to normalize.
- ⬜ 🟠 **`medicaid_level` and `language` are free-text inputs; make them pickers.** `editable_field()` renders a plain text box for every field. The engine behind it is fine — `customer_set_field` → `cp.set_human_value()` with provenance + conflict detection — so this is a template/macro change plus a vocabulary decision, **not** a rewrite. Medicaid intended values are documented on the model (`Full / QMB / SLMB / QI / None`); language needs a short list (Tim's Spanish-only customers via Mike L are the grounding case) with an "other" escape.
- ⬜ 🟠 **`lead_source` is display-only AND unwired.** Rendered as a plain `detail-row` in `customer_profile.html`, and it is **not in `cp.PROVENANCE_FIELDS`**, so the inline editor would reject it even if the template offered one. Needs adding to the field list + a picker (`pharmacy_referral / self_generated / referral / transfer` are the values already in the model comment).
- ⬜ 🟠 **Customer names ARE editable — the profile just never exposes them.** `first_name` / `last_name` / `preferred_name` are all in `PROVENANCE_FIELDS` and `customer_set_field` accepts them; the template simply doesn't render them via `editable_field()`. ⚠ Not obviously a bug: BOB imports own these names, and the `before_insert/before_update` event keeps `full_name` in sync. **Decide deliberately** — exposing them is a two-line template change, but agent edits then compete with carrier imports (that is what `manually_edited` and the trust ladder exist for, so the machinery is already there).
- ⬜ 🔴 **`Customer.pharmacy_id` conflates TWO different facts — this one is a real data-model problem, not a UI gap.** It FKs to `pharmacies`, and the profile dropdown lists partner pharmacies only, so a customer who fills at a **non-partner** pharmacy cannot be recorded at all. The field currently means both *"which partner pharmacy owns this relationship"* (business: rent, lead attribution, the Pharmacies-page analytics) and *"where does this person actually fill"* (clinical: the input to reimbursement and therefore to the winners/losers plan analysis). Those were the same thing when every customer used a partner; the book has outgrown that. **Forcing a non-partner into the partner FK would corrupt the pharmacy analytics; leaving it blank loses the fill location entirely.** → **separate the two fields**; brainstorm→spec. Ties directly to the Rx/reimbursement work (PioneerRx reports only see partner-pharmacy fills, which is why non-partner customers fall out of every drug-level report today).
